# 変異検査 — 「検査の検査」

## 原則

**緑のテストは「守れている」の証明にならない。守りを外して赤くなり、その赤が正しい理由であるときだけ、テストは守っている。**

実務での観測: 「誤った理由の緑」は繰り返し出る。ただし緑の正体は2つある — **守りが不在**か、**変異が弱めていなかった**か。後者を先に潰す(手順2)。後者を「守りが不在」と誤診しかけた例が実務で複数回観測されている。

## 手順(順序を守る)

1. **守りを外す(変異を入れる)** — 対象の1行をコメントアウト/条件反転する。
2. **変異が当たったこと自体を確かめる** — これが最も省略されやすい。
   - `grep -c` で変異後のコードに目印が残っている/消えていることを数える
   - テスト実行の件数(例: Pest の JSON 出力なら `"tests": N`)が変異前と同数か確認(0本なら変異ではなくテスト側が死んでいる)
   - **キャッシュを無効化する**: Blade なら `php artisan view:clear`、config なら `config:clear`。変異したのに古いコンパイル結果が動いていれば「変異が当たっていない緑」になる。同型: **build 済みの実行物(dist 等)を起動する試験は、src だけ変異しても素通りする** — 変異後に build し直してから走らせる(実際に1回空振りした実例)
3. **赤の理由を読む** — 赤くなった「から」OK ではない。失敗メッセージが**期待した違反**を言っているか読む。別の例外(クラス不在・構文エラー)で赤いのは「誤った理由の赤」で、テストは何も証明していない。
4. **復元して緑に戻す** — 復元後の緑も確認して初めて1サイクル完了。復元は**変異前に取った退避コピー(cp)から**行う — `git checkout -- <file>` は未 commit の実装ごと HEAD へ戻し(untracked の新規ファイルはそもそも戻らない)、実装が消えたまま「全変異赤」を報告する事故が実際に起きた。git で戻してしまったら、復元後に**全変異を回し直す**。
5. **等価変異は記録する — ただし「等価」と「見ないと決めた」を混ぜない。** 等価 = 出力が1文字も変わらない(仕様上区別がつかない)。出力は変わるのに試験が気づかないのは**生き残った変異**で、pin しないと決めたなら「変異は生き残るが承知のうえ」と書く。等価と書くと穴が穴として残らない — 「見なくてよい」と「見ないと決めた」は次の読者にとって別物。

## 変異が緑のとき、まず入口を疑う

生き残った変異の最頻出原因は「試験が、人の通る道と別の入口から入っている」こと(実例3件: 検査が import しただけで対象を直してしまう / fixture が描画されない形で assert が空を見る / Writer を直接呼ぶ試験は Draft の検証を通らない)。変異が緑なら、等価かどうかを考える前に「この試験はどの入口から入ったか・人と同じ道か」を見るのが速い。

## 対照実験

「この守りを**足した**」と主張するときは逆向きに: 守りを外した世界で赤・戻した世界で緑、**両方**を実測してから主張する。片側だけの実測は「両方の世界で成立する条件」を見落とす — fixture が「区別の要る場合」を作っていないと、守りの有無に関わらず緑になる。

## fixture の設計

**「0件である」を主張する検査には canary を先に流す。** 0件になる理由は「違反が無かった」と「見張っていなかった」の2つあり、素朴な assert は両方を緑にする。わざと1件出して捕まることを確認 → リセット → 本番の計数、の順にする(空振りの自己捕獲)。**針(検査)と canary は1つの単位で足す** — 針だけ足して canary を忘れる再発が同一 round 内でも起きた。座の設計で「針が刺さる入力」を針と一緒に export すると、忘れが型で見える。同様に**静的な守りを外したら、代わりの動的な守りに試験を**(外した側にだけ試験がある片肺の実例)。canary は**検査対象と同じ導出で**作る — 手書きの文字列 canary は、導出側を壊しても緑のまま(実例: 導出を殺しても 11 本全緑)。

テストデータは**変異したときだけ区別がつく**形にする。「変異が赤 = 守れている」ではない — **その変異が通る道に fixture が居たか**が本当の条件(割当先2件の fixture は count===1 への弱体化を偶然捕まえるが、1件で別対象を指す fixture が居ないと value 確認の欠落は素通りする、という実例)。守りたい境界の**すぐ内側と外側**に fixture を置く。複数の守りが並ぶ場所では**1つずつ別々に踏ませる** — 同時に踏むと、1つ外しても他が代わりに赤くして「外したことが見えない」(4検査を同時に踏む fixture で、どれを外しても全緑だった実例)。例:「下書きが検索に出ない」なら、同じ語を持つ公開記事と下書き記事を**両方**用意し、「公開は出る」「下書きは出ない」を同時に assert する。片方だけだと空実装でも緑になる。

**根にあるのは1つ: 試験は、自分で作った世界しか通らない。** 生き残った変異を6例並べたら、通らなかった世界が毎回違うだけで(利用者の型構成 / preserve モード / 別の取り込み経路 / 型を作った後 / 公開した後 / 過去の記録)、原因は同一だった。**「この試験が絶対に作れない世界はどれか」**を先に1つ挙げると、穴の位置が名指しできる。

**偶然一致する fixture は、無いのと同じ。** 2つの導出規則を比べる試験では、たまたま同じ結果になる題材を選ぶと「導出できる」と読めてしまう(実例: 型名からクラス名を導く規則で、`news` は2つの世界が偶然一致し `works` だけが食い違う — `news` で測れば「`type` から導ける」と誤読できた)。**差が出る題材を名指しで選ぶ。**

**過去の記録を読む枝は、新しく作った fixture では絶対に踏めない。** 生成器を呼んで作った入力は常に最新の形になるので、旧形式を読む後方互換の枝は素通りする(実例: v1 の plan を読む枝を殺しても 752/752 緑 — 試験が毎回 `buildPlan()` で新形式を作っていた)。**commit 済みの現物をそのまま読む試験でしか踏めない。** 害の形は「落ちる」ではなく**静かに0件**なので、緑のまま配布物に載る。

## Red Flags — これを考えたら手を止める

| 思考 | 現実 |
| --- | --- |
| 「緑だから大丈夫」 | 緑は「テストが通った」以上の意味を持たない。守りの存在は変異でしか証明できない |
| 「変異したら赤くなった、OK」 | 赤の**理由**を読んだか? 構文エラーの赤は証明ではない |
| 「変異を入れて実行した」 | 変異が**当たった**ことを確かめたか? キャッシュ・コンパイル済み view・別ファイルの同名実装が古いまま動いていないか |
| 「時間がないので今回は省略」 | 省略した変異検査の穴は、後日監査で F 番号になって返ってくる |
