# 機能追加前の照合

<!-- 2026-09-18: 全修正への固定探索を外し、重複実装を防ぐ判断基準に絞る。 -->
対象機能が既にあるか、どの利用経路で不足しているかを確かめる。既知箇所の小さな修正に全体監査を課さない。

- 画面だけで判断できなければ、共通layout、Core/Modules、schema/registry、該当ADRまで必要な経路をたどる。
- 検索は実装上の別名も使う。1語の0件だけで機能不在と断定しない。
- 既存実装がある場合も、依頼された利用経路で動くかを確認する。実装やテストの存在だけでは完了としない。
- 複数機能の監査では、実装済み・不足・未確認と根拠を表にする。単一修正は短い説明で足りる。
- 同じ不具合が複数経路で見つかったら、共通原因と影響範囲を調べ、実際の出力・利用経路を守る検証を選ぶ。

過去の仕様と現行実装が食い違う場合は、差と影響を示す。依頼の意図を満たす局所修正は進め、製品仕様を選び直す判断だけ確認する。
