# 固定 commit 監査 — 読むだけでなく測り直す

## 原則

**報告は主張であって証拠ではない。監査は「報告された commit そのもの」を対象に、報告と同じ数字を自分の手で出し直すこと。repo には1バイトも変更を加えない。**

## 手順

1. **対象を固定する。** 作業ツリーではなく報告された commit hash を読む: `git show <hash>:<path>`(固定 blob)。作業ツリーは監査中にも動き得る — 「どの版を監査したか」が言えなくなる。
2. **「直る前」を先に測る — ただし適用場面を選ぶ。** 「直した」という主張がある commit では、diff を読む前に**親 commit**(`<hash>~1`)または当時の実測で、欠陥が再現する/テストが赤いことを押さえる。これが無いと「元から直っていた」「テストが元から緑(=何も検知しない)」を見逃す。**新機能の commit には「直る前の欠陥」が無い**のでこの手順は当たらない — そこでは変異検査が主になる。親 commit と変異は別の問いに答える(親 commit =「本当に壊れていたか」、変異=「その検査は欠陥を検知できるか」)。必要なら両方使う。
3. **数字は全部出し直す。** 「12本緑」と報告されたら12本を自分で走らせて数える。件数・skip 数・assertion 数まで。報告と食い違ったら、それ自体が発見。
4. **読みと実測を分離して書く。** 報告書では「diff を読んで分かったこと」と「実行して測ったこと」を別の節にする。読みだけの結論を実測のように書かない。
5. **測れなかったものは「測れなかった」と書く。** 環境が無い(MySQL・実ブラウザ・外部 API)なら、その範囲は PASS ではなく「未測定」— 誰の warrant かを明記する。黙って PASS に含めるのが最悪。
6. **位置と到達性を疑う。** 最頻出の欠陥型は「部品は正しいが、正しい位置に無い/そこから到達できない」。関数が正しくても、呼ばれているか・route が繋がっているか・middleware の順序で届くかを別途確かめる。
7. **CSP・nonce・インライン制限に触れる commit は、実ブラウザで1画面開いて console を見る。** 出力に nonce が載っていることは、実行時に弾かれないことを意味しない。弾かれても画面は 200 で、見た目も変わらないことがある — console だけが言う。**「0件」を名乗るときは読み込み時だけでなく操作後(開く・選ぶ・遷移する)も数える** — 読み込み時 0 件でも、UI ライブラリが操作時に style を挿して弾かれる例が実際に見逃された。報告には**「何を押したあとの 0 か」**を書く — 押していないなら「読み込み時のみ」と明記する(0 件は測った範囲とセットでないと warrant にならない)。
8. **指し先を開く。** 報告や docs の「〜に記録してある」「〜を参照」は、指した先を実際に開いて中身が在ることを確かめる(書いた時点で正しくても、置き場所が別なら外れる — 同型の外れが実務で繰り返し観測されている)。

## 報告様式

- 結論を先に(PASS / 指摘 N 件)。指摘には番号を振る(番号は監査報告の見出しが定義する)。
- 各指摘に: 事実(実測値) / なぜ害か / 直し方の案。
- 末尾に固定文: 「repo・docs・Git は無変更です」+ 測っていない範囲の一覧。

## Red Flags

| 思考 | 現実 |
| --- | --- |
| 「diff を読んだ、正しそう」 | 読みは実測ではない。数字を出し直したか |
| 「テストを流したら緑」 | 親 commit で赤だったか? 元から緑なら何も証明していない |
| 「報告の数字と一致した」 | どの commit で測ったか固定したか。作業ツリーは動く |
| 「この環境では測れないので省略」 | 省略は書けば warrant、黙れば嘘になる |
