# Release cut — 版と成果物の作法

## 原則

**同じ版番号が2つの中身を指した瞬間、版は意味を失う。cut の作法は全てこの事故の防止に向いている。**

## cut の手順

1. **版の正本を全部揃える。** 版番号を持つファイルは複数在る(例: `VERSION` と `packages/cli/package.json`)。全部を同じ値にしてから cut する。1つでも古いと「版の正本が割れる」。
2. **SHA は git に記録する。** 成果物そのものは git 外でも、`SHA256SUMS`・manifest 等の**記録**は commit する。「どの commit がこの成果物を作ったか」(`created_from_commit`)も成果物側に残す — 後から「この zip はどこから来たか」を双方向に辿れる。
3. **三重一致を確認する**: ① 成果物外側の `.sha256` ② bundle 内の `SHA256SUMS` ③ manifest の記録。`shasum -a 256 -c` を実際に実行し、1つでも NG なら配布しない。
4. **前版の無傷を確認する。** cut の**前に**既存版の SHA を控え、cut の**後に**同じ値であることを比較する。「新しい版を切るついでに前の版が書き換わる」事故はここでしか捕まらない。

## 再 cut(切り直し)の判断

**境界線は「配布済みか」。**

- **未配布** → 同じ版番号で**入れ替え**る(旧成果物は残さない・並べない。並べると「どちらが正か」が言えなくなる)。上書きの門(`--force`)は迂回せず、**理由と新旧両方の SHA を commit message に明記**することで「在るものを黙って作り直さない」の主旨を満たす。
- **配布済み**(タグ push・ストア登録・1人にでも送付) → その版は不変。修正は**次の版番号**で切る。

## 再 cut 後の検証

- **「変わったものだけが変わった」を差分で確かめる。** 直したのが zip 直下のファイルだけなら内部 tgz の SHA は不変のはず。変わるはずのないものが変わっていたら、何かが混入している。
- 修正が**成果物の中に届いたか**を開いて目視する(repo のファイルを直しても、利用者が持つのは cut 時点の中身)。
- 法的文書(LICENSE 等)は説明文の修正で触れない — SHA が不変であることで「触れていない」を証明できる。

## Red Flags

| 思考 | 現実 |
| --- | --- |
| 「未配布だから黙って作り直せばいい」 | 上書き自体は正しいが、黙るのが事故。理由と両 SHA を commit に残す |
| 「rebuild したら SHA が変わった、当然」 | **何が**変わったかを内訳(内部 tgz・各ファイル)で確認したか |
| 「repo の README を直した、完了」 | 成果物の中の README は古いまま。切り直さなければ利用者に届かない |
| 「旧 zip はバックアップとして残す」 | 未配布なら残さない。同版2成果物は「どちらが正か」を壊す |
