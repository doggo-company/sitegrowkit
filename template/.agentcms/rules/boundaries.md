# Module Boundaries (MUST follow)

## Core vs Project

- `core/` (= `agentcms/core`) is CMS Core. **Inside a generated project it is read-only.** Never modify, never copy-paste its classes out to "customize".
- Site-specific work goes in: `app/` (thin glue), `modules/<name>/` (content type impl + public templates), `content/schemas/` (content type definitions), `resources/` (views, admin pages).
- Extend Core ONLY via its published extension points: interfaces/events/config under `core/src/Contracts/` and `core/config/`. If an extension point is missing, that is a kit-level change (ADR + core release), not a local hack.
- Do not add dependencies from `core/` to `app/` or `modules/` — dependency direction is always project → core.

## Module locality

A module owns everything about its content type, close together.
PSR-4 is `Modules\<Name>\` → `modules/<Name>/` (PascalCase dir, no src/ segment — adding a module never requires composer.json edits):

```
modules/<Name>/
├── (schema lives in content/schemas/<name>.json — one place, do not copy)
├── Models/               # Modules\<Name>\Models\...
├── Http/                 # controllers if needed
├── database/migrations/  # auto-loaded by ModulesServiceProvider
├── views/                # Blade, namespaced view('<name>::...')
└── tests/                # Pest tests for this module
```

Don't scatter a content type's logic across global folders when it can live in its module.

Modules created by the admin Content Type Builder (`"managedBy": "cms"` in the schema) follow the same layout but are **generated** — they carry a `generated by agentcms content type builder` marker. Don't hand-edit them: change the schema and the generator, or the next regeneration/verification will disagree with the file.

## Admin vs Public

- Admin UI: Inertia + Vue + TS + Tailwind/shadcn-vue. Schema-driven — do not hand-build one-off CRUD screens when the schema can drive it.
- Public site: Blade SSR + plain CSS. Tailwind is FORBIDDEN in public site CSS. Vue only where interaction requires it (e.g. Turnstile widget glue).

## Project Scope Schema Override (ADR-0010 Rev.1)

- kit-standard schemas in `content/schemas/*.json` should stay as shipped. When a project needs different field attributes (e.g. a template import where the design has no `category` concept), put a field-attribute patch in `content/schemas/overrides/<id>.json` — SchemaRegistry merges it at load time. Never edit the kit-standard schema file for a project-specific reason.
