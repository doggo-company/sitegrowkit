# Coding Rules (MUST follow)

## General

- Read `.agentcms/context/map.md` and the relevant module before exploring the whole repo.
- Schema first: to add/change a content type field, edit `content/schemas/<type>.json`, never hand-edit admin forms/validation to diverge from schema.
- No speculative abstraction. No "while I'm here" refactors. One request = one change unit.
- UTF-8 (no BOM). PHP: Pint (Laravel preset). TS/Vue: ESLint + project prettier config.
- PHP: constructor property promotion, typed properties, enums for fixed value sets, no raw SQL string concatenation (Eloquent/Query Builder only).
- TS: strict mode, no `any` unless justified with a comment.

## Preserve First (HTML template import)

When importing or touching existing HTML/CSS/JS templates:

- Do NOT convert CSS to Tailwind
- Do NOT rename classes
- Do NOT "improve" the visual design uninvited
- Do NOT Vue-ify markup that has no interaction need
- Read the inspect Manifest (`agentcms template inspect`) before reading raw template files
- Follow the pipeline order: inspect → plan (review REVIEW/UNKNOWN items) → apply → template verify. Never hand-edit generated files marked `generated by agentcms template apply` (re-apply will flag them as conflicts) — change the generator or the source template instead

## Manifest First (Figma import)

- Read the Design Manifest (`agentcms figma inspect` → `.agentcms/manifest/figma.json`) — never the raw cache under `.agentcms/cache/figma/`. Raw cache is client design data, not AI context (ADR-0011).
- Follow the pipeline order: connect → inspect → plan (review REVIEW/UNKNOWN) → human approval → apply → figma verify. Figma is read-only: apply writes to the local project only; never call Figma write APIs / MCP write tools / Code Connect publish.
- Never copy Figma x/y into `position:absolute` layouts; translate Auto Layout intent (flex/grid) instead. Never invent content the design doesn't contain — missing content is REVIEW.
- Token precedence: Figma Variable > Style > Inferred. Don't tokenize every value (frequency threshold), and never rewrite existing project CSS tokens to match Figma — conflicts are surfaced in the plan for humans.

## Blade / Vue split

- Public pages: Blade SSR. JS only where interaction demands it.
- `{!! !!}` (raw echo) is forbidden except for sanitized CMS body HTML rendered through the core purifier helper.
- Admin pages: Inertia + Vue + TS, shadcn-vue components, schema-driven forms via core.

## Tests

- Every module carries its own Pest tests (see rules/testing.md).
- Never mark work done on green words — run the gate: `agentcms verify`.

## Dependencies

- After `composer require <pkg>`, check the resolved major against `composer show <pkg> --all` — an old transitive constraint can silently pin an outdated major (Phase 3: web-push resolved to v8 whose safe v2 dep sprays PHP 8.5 deprecation warnings into every HTTP response; v11 was available and clean).
- **The lock file must be resolved for the MINIMUM supported PHP, not the dev runtime.** `composer.json` pins `config.platform.php` to the declared minimum (currently 8.3.0) — never remove it. Without the pin, a newer dev PHP (Docker 8.5) silently resolves deps that require a higher PHP (Phase 4: Symfony 8.1 requires >= 8.4.1 → every request 500s on an 8.3 host via vendor/composer/platform_check.php, while composer.json still claims `php ^8.3`). After changing the pin or PHP requirement, run `composer update` and re-run the full gate + E2E.

## Larastan patterns (learned in Phase 2 — avoid re-discovering)

- `Collection->values()->all()` is NOT inferred as `list<>`; wrap with `array_values()` when a docblock promises `list<>`.
- After `assertSame([], $x->foo($id))`, PHPStan pins later identical calls to `array{}` — split state-changing tests into separate methods instead of asserting empty-then-nonempty on the same expression.
- `$response->getContent()` returns `string|false` — cast with `(string)`.
- Verifying multi-line HTML output: don't pipe curl into single-line `grep`; use `tr -d '\n'` first, or assert in Pest/E2E instead.
- Run `pint` (auto-fix) before `agentcms verify` — the verify gate runs `pint --test` and will fail on unformatted new files.

## select / taxonomy / relation の使い分け（Phase 9.3B）

分類を足すときは、まずこの 3 つのどれなのかを決める。混同すると後から作り替えになる。

| | 用途 | 値 | 管理 |
| --- | --- | --- | --- |
| `select` | schema 内に固定 choices を持つ。独立した分類管理を必要としない | 文字列 | schema ファイルを編集する（コード） |
| **taxonomy** | Term を独立管理する。hierarchy / order / archive / assignment を持つ | Term ID | 管理画面から追加・並べ替え・アーカイブ |
| `relation` | 別 Content Entry **そのもの**への参照 | Entry ID | 参照先の Content Type を管理 |

**select を選ぶ条件**

- 選択肢が滅多に増えない（ステータス・種別など）
- hierarchy・term の並べ替え・アーカイブ・横断 filter を必要としない

**taxonomy を選ぶ条件**

- 運用中に増減する（カテゴリ・タグ）
- listing filter や分類アーカイブの対象になる
- checked-in の ContentSchema では **taxonomy key** を参照する（`taxonomies[]`）
- runtime の assignment では **immutable な term ID** を使う
- **checked-in JSON へ ULID を書かない**

**relation を選ぶ条件**

- 指したいものが「分類語彙」ではなく具体的なエントリ
- taxonomy assignment の代用にしない

`works.category` は現時点では **select のまま**である。taxonomy への移行は別 Gate（Phase 9.3C）で扱う。

### `taxonomies` は予約キー（MUST）

`taxonomies` は **ContentSchema のトップレベル field key として使えない**。

- content payload は `{"data": {...}, "taxonomies": {...}}` の形で、`taxonomies` は分類の割り当て専用
- read response も `item.taxonomies` に分類を返す
- 同名の通常 field を許すと、値が黙って落ちたり分類 block に上書きされたりする

したがって `content/schemas/*.json` のトップレベル `fields[].key` に `taxonomies` があると、
schema の読み込み自体が失敗する（`agentcms verify` / `agentcms:taxonomy-check` が
**データベースへ接続する前に** FAIL する）。別の名前へ変更すること。

**入れ子（`group` / `repeater`）の子フィールド名は対象外**で、従来どおり `taxonomies` を使える
（`data` JSON の中で完結し、トップレベルの表現と衝突しないため）。
